## Codebase Patterns
- Provider-level RediSearch APIs should construct a `RedisQuery` and then delegate to `SearchAsync(RedisQuery)` so new entry points keep the shared FT.SEARCH serialization and execution path.
- When a command-oriented query should target a mapped Redis OM document type, construct `RedisQuery` from the document `Type` so index resolution stays tied to `[Document]` metadata instead of duplicating index-name strings.
- Provider overloads that add projection behavior should accept `ReturnFields` directly instead of `params string[]`, because the command-oriented API already uses `object queryParameters` and string-based overloads become ambiguous for callers.
- Projection hydration should treat Redis field names as lookup keys and CLR property names as JSON output keys, so typed DTO projections can rely on `ReturnField` aliases or `[RedisField(PropertyName = ...)]` without breaking deserialization.
- When an ad hoc projection shape is needed, prefer a dedicated helper type hydrated inside `SearchResponse<T>` over a new provider overload, so callers keep using the same `SearchAsync<T>(RedisQuery)` execution path and only swap the result type.
- Manual `RedisAggregation` pipelines serialize `Predicates` in stack order, so command-oriented examples and tests need to push later stages first when composing a pipeline directly.
- Typed aggregation row mapping should reuse `AggregationResult<T>.Hydrate<THydrated>()` and `RedisObjectHandler.FromHashSet<T>` so aggregation DTOs follow the same alias and `[RedisField(PropertyName = ...)]` rules as search projections.
